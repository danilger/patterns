# Compound Components

**Область:** Frontend / React  
**Источники:** [patterns.dev — Compound Pattern](https://www.patterns.dev/react/compound-pattern); Addy Osmani, *Learning Patterns*, Ch.12

---

## Смысл паттерна

**Compound Components** — это способ спроектировать API виджета как **набор связанных компонентов**, которые вместе образуют один UI-элемент и **делят неявное состояние**.

Вместо одного монолитного компонента с кучей пропсов:

```jsx
<Tabs
  tabs={["Profile", "Settings"]}
  panels={[<Profile />, <Settings />]}
  activeIndex={0}
  onChange={...}
/>
```

потребитель **собирает** интерфейс декларативно из частей:

```jsx
<Tabs>
  <Tabs.List>
    <Tabs.Tab index={0}>Profile</Tabs.Tab>
    <Tabs.Tab index={1}>Settings</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel index={0}>…</Tabs.Panel>
  <Tabs.Panel index={1}>…</Tabs.Panel>
</Tabs>
```

Родитель (`Tabs`) владеет состоянием (какой таб активен). Дети (`Tab`, `Panel`) читают и меняют его **без явной передачи пропсов снаружи** — обычно через Context (или через замыкание / фабрику, как в демо-файле).

Ключевая идея: **родитель и дети — один логический виджет**, а не независимые компоненты, случайно лежащие рядом.

---

## Что решает

| Проблема | Как помогает Compound |
|----------|------------------------|
| Жёсткий API (`tabs={[]}`, `panels={[]}`) | Разметка гибкая: порядок, вложенность, лишние обёртки — на стороне потребителя |
| Prop drilling между частями виджета | Состояние «живёт» в корне и доступно детям неявно |
| Смешение структуры UI и логики | Логика в родителе; дети — тонкие «роли» (вкладка, панель, триггер) |
| Дизайн-система с вариациями разметки | Один контракт (`Tabs.*`), много допустимых композиций |

Потребитель описывает **структуру**, библиотека — **поведение**.

---

## Как это устроено

### 1. Корень (Compound parent)

- Хранит общее состояние (`active`, `open`, `value`).
- Предоставляет его потомкам (Context / замыкание).
- Часто экспортирует подкомпоненты как свойства: `Tabs.Tab`, `Tabs.Panel`.

### 2. Подкомпоненты (Compound children)

- Знают свою **роль**: кликабельная вкладка, контейнер контента, список.
- Подписываются на общее состояние и реагируют на него.
- Не требуют, чтобы пользователь прокидывал `active` / `setActive` вручную.

### 3. Неявное состояние

«Неявное» значит: снаружи не видно `activeIndex` на каждом ребёнке. Связь «вкладка ↔ панель» обеспечивается внутри семейства компонентов, а не пропсами на каждой странице приложения.

## Связь с демо в `compound-components.js`

Файл без React показывает ту же идею на замыкании:

1. `createTabs()` создаёт **общий `state`** и API (`setActive`, `subscribe`).
2. `Tabs.Tab` / `Tabs.Panel` — части одного виджета; они замыкаются на этот `state`.
3. `Tab.select()` меняет активный индекс → подписчики и `Panel.isActive()` видят одно и то же значение.

В React-комментарии внизу файла та же схема через `TabsContext`: родитель — Provider, `Tab` читает `active` / `setActive` из Context.

```
createTabs() / <Tabs>     →  владелец state
Tabs.Tab / Tabs.Panel     →  роли с доступом к state
subscribe / useContext    →  неявная связь частей
```

## Классические примеры

- **Tabs** — `Tabs` + `Tabs.List` + `Tabs.Tab` + `Tabs.Panel`
- **Select** — `Select` + `Select.Option` (или `Option`)
- **Accordion** — `Accordion` + `Accordion.Item` + `Header` + `Panel`
- **Menu** — `Menu` + `Menu.Button` + `Menu.List` + `Menu.Item`
- HTML-аналогия: `<select>` + `<option>` — нативный compound API браузера

---

## Когда применять

- Гибкий API дизайн-системы: меню, табы, аккордеон, combobox.
- Родитель и дети **обязаны** работать вместе как один контрол.
- Нужна свобода в разметке (порядок детей, обёртки, кастомные слоты), но общее поведение должно оставаться согласованным.

## Когда не стоит

- Компонент простой и всегда выглядит одинаково — достаточно одного компонента с пропсами.
- «Дети» на самом деле независимы и не делят состояние — это обычная композиция, не compound.
- Нужен полный контроль снаружи (controlled-only API) без внутренней связки частей — лучше явные пропсы / render props / хук.

---

## Связь с другими паттернами

| Паттерн | Отличие |
|---------|---------|
| **Provider / Context** | Транспорт состояния; Compound — *способ спроектировать API* поверх него |
| **Render Props / Hooks** | Тоже гибкость, но через функции, а не через декларативное дерево детей |
| **Container / Presentational** | Разделение логики и вида; Compound — про *семейство* связанных частей одного виджета |
| **Composite (GoF)** | Дерево «часть–целое» с единым интерфейсом; Compound в React — про UX API и shared state, не про рекурсивный `getSize()` |

---

## Краткий итог

Compound Components = **виджет как набор ролей** (`Tabs` + `Tab` + `Panel`), где состояние общее и неявное, а потребитель собирает UI декларативно. Смысл паттерна — не «использовать Context», а дать **выразительный и гибкий API**, в котором структура разметки принадлежит пользователю, а согласованное поведение — родителю.
