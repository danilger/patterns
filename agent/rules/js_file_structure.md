# Структура JS/TS-файла

Правило для агентов: форма модуля и порог декомпозиции.

## Сначала экспорт

В модуле основной runtime-экспорт идёт **сразу после импортов**
(с JSDoc, если это компонент, хук или публичный API).

Всё остальное — **ниже** в помеченных секциях либо в отдельных файлах:

1. Imports
2. Зона основного экспорта — только runtime-экспорты
   (`export function` / `export const` / `export class`, …)
3. `// HELPERS` — локальные функции / схемы, которыми пользуется экспорт
4. `// TYPES` — `type` / `interface` (включая props и result-типы)
5. По необходимости: `// CONSTANTS`, `// STYLES`

Правила:

- Маркер секции ставь только если в секции есть содержимое.
- В зоне основного экспорта не держи хелперы, типы и прочие
  неэкспортируемые объявления.
- Приоритет: сначала держи хелперы/типы в секциях того же файла;
  выноси в соседний или `model/` domain-named файл, если секция мешает
  читать экспорт, разрослась, или появился второй consumer.

## Размер

Файл длиннее **~100 строк** — сигнал к декомпозиции (вынести helpers/types,
разделить UI-секции или вынести оркестрацию в хук), а не повод дробить
«на всякий случай». Один экран / один хук / один store в одном файле —
нормально, даже если чуть длиннее, пока нет второй ответственности.
Лучше меньше ясных модулей, чем много крошечных.
