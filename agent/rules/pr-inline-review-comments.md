# Inline-комментарии в PR/MR

Правило для агентов: после открытия или обновления pull/merge request
обязательны **общий комментарий к PR/MR** и **inline review comments на
diff**.

## Жёсткая норма

Когда открываешь или обновляешь PR/MR на любом Git-хосте с line comments
на diff (GitHub, GitLab, Forgejo, Gitea, Bitbucket, …):

1. Опубликуй или обнови **общий комментарий к PR/MR** (описание PR/MR /
   body, не комментарий в трекере задачи):
   - короткое описание изменения (что сделано и зачем);
   - рекомендацию, **в какой последовательности** ревьюить изменённые
     файлы (нумерованный список путей + одна фраза, почему такой порядок).
2. Оставь **inline review comments на изменённых строках** этого PR/MR.
3. Inline — это **комментарии провайдера на diff** (review API /
   `gh` / `glab` / forge API) — **не** комментарии в исходниках
   (`//`, `#`, `/* */`, …) и **не** замена общего комментария к PR/MR
   или комментария в трекере задачи.
4. **Сам выбирай**, какие моменты ключевые для inline. Предпочтай
   объяснения с высокой ценностью (intent, неочевидные trade-off’ы,
   риски, контракты, edge cases). Пропускай тривиальный churn
   (rename-only, formatting, boilerplate).
5. PR/MR без общего комментария (описание + порядок ревью) или без
   inline-комментариев — **неполная сдача**. Не считай работу
   завершённой, пока они не опубликованы, либо пока не убедился, что
   хост не умеет line comments / auth блокирует их — тогда явно напиши
   об этом в комментарии к задаче; не подменяй inline комментариями в
   коде.

Если провайдер вообще не поддерживает line comments на diff — скажи
об этом один раз и используй ближайший поддерживаемый механизм ревью
(например, file-level note). Никогда не подменяй это комментариями в
исходных файлах. Общий комментарий с описанием и порядком ревью всё
равно обязателен.

## Общий комментарий — что писать

- **Описание:** 2–5 предложений: цель изменения, границы (что не
  трогали), как проверить.
- **Порядок ревью:** нумерованный список только значимых изменённых
  файлов (можно сгруппировать связанные). Порядок — от контрактов /
  модели / ядра к UI, тестам и косметике (или иной логичный поток для
  этого PR). У каждого пункта — одна короткая причина.
- Не дублируй весь diff и не перечисляй trivial churn без нужды.

Пример формы:

```markdown
## Summary
…

## Suggested review order
1. `path/a.ts` — …
2. `path/b.tsx` — …
3. …
```

## Inline — что писать

- Объясняй **почему** этот hunk важен ревьюеру, а не пересказывай diff.
- Держи каждый комментарий коротким и привязанным к строкам якоря.
- Лучше небольшой набор точных комментариев, чем спам; качество важнее
  количества.
