# Inline-комментарии в PR/MR

Правило для агентов: после открытия или обновления pull/merge request
обязательны **inline review comments на diff**.

## Жёсткая норма

Когда открываешь или обновляешь PR/MR на любом Git-хосте с line comments
на diff (GitHub, GitLab, Forgejo, Gitea, Bitbucket, …):

1. Оставь **inline review comments на изменённых строках** этого PR/MR.
2. Это должны быть **комментарии провайдера на diff** (review API /
   `gh` / `glab` / forge API) — **не** комментарии в исходниках
   (`//`, `#`, `/* */`, …) и **не** только описание PR/MR или комментарий
   в трекере задачи.
3. **Сам выбирай**, какие моменты ключевые. Предпочтай объяснения с
   высокой ценностью (intent, неочевидные trade-off’ы, риски, контракты,
   edge cases). Пропускай тривиальный churn (rename-only, formatting,
   boilerplate).
4. PR/MR без таких inline-комментариев — **неполная сдача**. Не считай
   работу завершённой, пока они не опубликованы, либо пока не убедился,
   что хост не умеет line comments / auth блокирует их — тогда явно
   напиши об этом в комментарии к задаче; не подменяй inline
   комментариями в коде.

Если провайдер вообще не поддерживает line comments на diff — скажи
об этом один раз и используй ближайший поддерживаемый механизм ревью
(например, file-level note). Никогда не подменяй это комментариями в
исходных файлах.

## Что писать

- Объясняй **почему** этот hunk важен ревьюеру, а не пересказывай diff.
- Держи каждый комментарий коротким и привязанным к строкам якоря.
- Лучше небольшой набор точных комментариев, чем спам; качество важнее
  количества.
