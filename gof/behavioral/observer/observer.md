# Observer (Наблюдатель)

**Область:** Behavioral / GoF

---

## Смысл паттерна

**Observer** задаёт зависимость **«один ко многим»**: при изменении **Subject** все подписанные **Observer**'ы получают уведомление и обновляются. Subject не знает конкретных классов наблюдателей — только общий интерфейс `update()`.

Это основа reactive-модели: UI подписывается на store, виджеты — на модель, микросервисы — на события домена.

```
Subject.setState() → notify() → Observer₁.update()
                              → Observer₂.update()
```

---

## Как устроено демо

В `observer.js` — **метеостанция** и дисплеи:

| Класс | Роль |
|-------|------|
| `Subject` | Реестр observers: `attach`, `detach`, `notify` |
| `WeatherStation` | Конкретный subject: `temperature`, `setTemperature()` вызывает `notify()` |
| `Observer` | Контракт `update(subject)` |
| `PhoneDisplay` | Печатает имя и текущую температуру |

Сценарий:

1. К телефону и планшету подписываются на станцию.
2. `setTemperature(22)` и `25` — оба дисплея реагируют.
3. `detach(tablet)` — планшет отписан.
4. `setTemperature(18)` — обновляется только телефон.

Push-модель: Subject сам рассылает уведомление при каждом изменении.

---

## Когда применять

- Изменение одного объекта должно **каскадно обновить** несколько зависимых (UI, кэш, лог, метрики).
- Связь **слабая**: наблюдателей можно добавлять и убирать в runtime.
- Event-driven архитектура, pub/sub, reactive streams — дух Observer.

**Не стоит**, если:

- порядок и транзакционность уведомлений критичны (нужен явный orchestrator / Mediator);
- слишком много подписчиков без debounce — риск «шторма» обновлений;
- проще **pull** (observer сам опрашивает subject) — иногда достаточно polling.

---

## Связь с другими паттернами

| Паттерн | Отличие |
|---------|---------|
| **Mediator** | Центральная координация A↔B; Observer — broadcast от одного источника |
| **Pub-Sub / Event Bus** | Часто с брокером между publisher и subscriber |
| **Reactive (RxJS, signals)** | Observer + композиция потоков и операторов |
| **MVC** | Model уведомляет View через observer-механизм |

---

## Краткий итог

Observer = **Subject уведомляет подписчиков** при изменении состояния. Подписчики не тянут subject за конкретным API — получают его в `update()`. В демо смена температуры автоматически обновляет все активные дисплеи.
